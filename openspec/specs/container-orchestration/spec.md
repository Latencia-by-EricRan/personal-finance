# Container Orchestration Specification

## Purpose

Defines the observable behavior of the root `docker-compose.yml` that orchestrates the full PersonalFinance stack (Mongo, `back`, `web`) as an additional, fully-containerized run option. This coexists with — and does not replace — `back/`'s native `./start-dev.sh` workflow.

## Requirements

### Requirement: Single-command full-stack startup

The system MUST allow starting Mongo, `back`, and `web` together from the repository root with a single Docker Compose command.

#### Scenario: Operator starts the full stack

- GIVEN the repository root contains `docker-compose.yml`
- WHEN an operator runs `docker compose up` at the repo root
- THEN Mongo, `back`, and `web` containers all start
- AND no additional manual steps are required to bring up any of the three services

### Requirement: Shared network for inter-service communication

All services defined in the root compose file MUST be attached to a shared Docker network, so containers can reach each other by service name.

#### Scenario: Back reaches Mongo by service name

- GIVEN the root compose stack is running
- WHEN the `back` container resolves its Mongo connection string
- THEN it MUST reach the `mongodb` container using the `mongodb` service name, not a host-loopback address

#### Scenario: Web reaches back by service name

- GIVEN the root compose stack is running
- WHEN the `web` container needs to call the backend API from server-side code
- THEN it MUST reach the `back` container using its Docker service name over the shared network

### Requirement: Mongo healthcheck gates back startup

The `back` service MUST NOT be considered ready to accept dependent traffic until Mongo reports healthy, mirroring the existing pattern in `back/compose.yaml`.

#### Scenario: Back waits for Mongo health

- GIVEN the root compose stack is starting up
- WHEN Mongo has not yet passed its healthcheck
- THEN the `back` service MUST remain in a waiting/not-started state
- AND `back` MUST only start once Mongo's healthcheck reports healthy

### Requirement: Host-reachable published ports

The root compose file MUST publish `back` and `web` ports to the host so a browser on the host machine can reach both services.

#### Scenario: Browser reaches back API from the host

- GIVEN the root compose stack is running
- WHEN a browser on the host requests `http://localhost:3000`
- THEN the request MUST reach the `back` container

#### Scenario: Browser reaches web app from the host

- GIVEN the root compose stack is running
- WHEN a browser on the host requests `http://localhost:4200`
- THEN the request MUST reach the `web` container

### Requirement: Native back/ workflow remains unaffected

Introducing the root compose file MUST NOT change or break `back/`'s existing native+Mongo-only development workflow.

#### Scenario: back/start-dev.sh keeps working

- GIVEN the root `docker-compose.yml` exists in the repository
- WHEN a developer runs `back/start-dev.sh` as before
- THEN the native API process and dockerized Mongo start exactly as they did prior to this change
- AND no root-compose-specific configuration is required for this workflow to succeed

### Requirement: Corrected CORS origin for the frontend

The `.env` file generated by `back/scripts/onboarding.mjs` MUST allow the actual frontend origin used by `web/` (port 4200), not the stale port from a prior frontend project.

#### Scenario: Onboarding generates a working CORS origin

- GIVEN a developer runs the onboarding script and no `.env` file exists yet
- WHEN the script generates a new `.env` file
- THEN the generated file MUST contain `CORS_ORIGINS=http://localhost:4200`

#### Scenario: Frontend requests are not blocked by CORS

- GIVEN `back` is running with a `.env` generated by the corrected onboarding script
- WHEN the `web` app running on `http://localhost:4200` makes a browser-side request to `back`
- THEN the request MUST NOT be rejected by CORS
