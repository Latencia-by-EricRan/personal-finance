# Exploration: Dockerizing the PersonalFinance monorepo (back/, web/, client-flutter/)

## Current State

**back/ — fully dockerized, real dev workflow already runs through it.**
- `back/Dockerfile`: multi-stage (`deps` → `dev` / `build` → `prod-deps` → `prod`), Node 22.22.3-alpine, `dev` target expects source bind-mounted at runtime, exposes 3000.
- `back/compose.yaml` (NOT `docker-compose.yml` — modern short filename): two services.
  - `mongodb`: `mongo:8`, port bound to `127.0.0.1:27017` only, named volume `personal-finance-mongodb`, healthcheck via `mongosh ping`.
  - `api`: builds `back/Dockerfile` target `dev`, `depends_on: mongodb (service_healthy)`, `env_file: .env`, overrides `MONGO_CONN_STR` to `mongodb://mongodb:27017` (service-name DNS) because the same `.env` also has to work for host-native `npm run dev`, which needs `127.0.0.1:27017`. Bind-mounts `.:/app` + anon volume for `/app/node_modules`. Publishes `3000:3000`.
- `back/start-dev.sh` → delegates to `back/scripts/onboarding.mjs`, which: checks Node version + `docker compose version`, `npm ci`, generates `.env` (`MONGO_CONN_STR=mongodb://127.0.0.1:27017`, `CORS_ORIGINS=http://localhost:5173`, JWT secret, seeded admin creds), runs `docker compose up -d mongodb` (only Mongo, NOT the `api` service), waits for health via `docker compose exec mongodb mongosh ping`, runs `npm run seed`, then starts the API **natively** via `npm run dev` (not via Docker). So the `api` service in `compose.yaml` is defined but unused by the actual documented dev workflow — it only activates if someone runs `docker compose up` directly instead of `./start-dev.sh`. Two parallel dev paths exist (native-with-dockerized-Mongo vs fully-containerized) and they're not both exercised by CI/scripts today.
- `back/.dockerignore` present and sane (`node_modules`, `dist`, `.git`, `.env`, etc.).
- **Bug already present, unrelated to Docker but relevant to any orchestration work**: generated `.env` sets `CORS_ORIGINS=http://localhost:5173` (Vite's default port) but `web/`'s actual dev server port is **4200** (Angular default, confirmed in `web/package.json` `"start": "ng serve"` and `web/CLAUDE.md`). This looks like leftover from a pre-Angular scaffold and would reject legitimate CORS requests from the real dev frontend today, Docker or not.

**web/ — NOT dockerized at all.** No `Dockerfile`, no compose file, no `.dockerignore` anywhere under `web/`. Confirmed by direct glob, not assumption.
- Angular 19 SSR, package manager **bun** (`web/bun.lockb` present), `package.json` `"name": "front"` (stale — leftover from before the `front/` → `web/` rename that the root `CLAUDE.md` doesn't reflect either; root `CLAUDE.md` still calls it `front/` throughout, which is now inaccurate).
- Already has `web/src/environments/environment.ts` and `environment.development.ts`, both exporting `apiUrl: 'http://localhost:3000'` — root `CLAUDE.md`'s claim that "API base URLs are hardcoded per-service, no environment-based config" is **stale**; there IS an environment abstraction (`MovementService.mainUrl = environment.apiUrl`), it's just that the value itself is still a hardcoded `localhost:3000` string in both environment files.
- **Confirmed real risk, not hypothetical**: `SummaryByMonthComponent` (`web/src/app/components/main-container/pages/records/pages/summary-by-month/summary-by-month.component.ts`) calls `this.movementSvc.getMovementsByMonth(...)` as an **eager field initializer** (not inside `ngOnInit` guarded by `isPlatformServer`), meaning the HTTP call fires during component construction — which Angular Universal also executes **server-side** during SSR. In a container, that server-side fetch would hit `http://localhost:3000` **from inside the `web` container itself**, not the `back` container — `localhost` there resolves to the web container's own loopback, so it would get `ECONNREFUSED` (no listener on that container's port 3000) unless something is changed. This is the single most concrete Docker-networking risk in the whole exploration; it is NOT solved by simply publishing ports to the host, because this specific call happens server-to-server inside Docker, not browser-to-host.
- Genuinely client-side (browser) calls, by contrast, are NOT broken by containerizing `web/`: the user's browser runs on the host machine, so `http://localhost:3000` resolves correctly there as long as `back`'s port 3000 is published to the host — no special Docker network wiring needed for those.
- `web/openspec/changes/archive/...` exists — `web/` already has its own independent OpenSpec history as a sub-project artifact store; this doesn't conflict with the root-level `openspec/changes/dockerize-monorepo/` being created for this cross-cutting change, but worth noting there are now two separate OpenSpec trees in this monorepo (one root-level for cross-project changes, one inside `web/` for web-only changes).

**client-flutter/ — already dockerized, narrower scope than back/.**
- `client-flutter/Dockerfile`: single stage, `ghcr.io/cirruslabs/flutter:stable` (explicit comment explains why not the abandoned `cirrusci/flutter` Docker Hub image), `flutter pub get`, exposes 8080, `CMD flutter run -d web-server --web-hostname=0.0.0.0 --web-port=8080`.
- `client-flutter/docker-compose.yml`: single `web` service, `build: .`, `8080:8080`, bind-mounts `.:/app` + anon volume `/app/build`, command re-runs `flutter pub get && flutter run -d web-server ...`. No dependency on `back`/Mongo declared in this compose file — it's fully standalone, self-contained, matching the "each sub-project owns its own Docker setup" pattern already established by `back/`.
- `client-flutter/.dockerignore` present (`build/`, `.dart_tool/`, `.idea/`, gradle/Pods caches).
- `client-flutter/lib/core/config/api_config.dart`: `baseUrl` resolves to `http://localhost:3000` when `kIsWeb` is true (browser context) or non-Android desktop; `http://10.0.2.2:3000` only for native Android emulator; there's a manual `hostOverride` static field for physical LAN devices. Since the web-server target serves compiled Dart-to-JS that executes in the **user's browser**, not server-side, the same "browser resolves localhost correctly via published host port" reasoning as `web/` applies here — no SSR-style risk for `client-flutter`'s web target specifically. The Android/native targets are out of Docker's scope entirely (mobile builds don't run in a container network at request time).

## Affected Areas
- `back/compose.yaml`, `back/Dockerfile`, `back/scripts/onboarding.mjs` — existing precedent/style to match; `onboarding.mjs`'s two-path dev workflow (native app + dockerized Mongo only) is a design precedent a root compose needs to either preserve or explicitly supersede.
- `back/.env` (generated, git-ignored) — `CORS_ORIGINS` mismatch vs `web/`'s real port.
- `web/environments/environment.ts` + `environment.development.ts` — `apiUrl` value would need to differ for "browser context" vs "server (SSR) context" if `web/` runs inside a container network alongside `back/`.
- `web/src/app/.../summary-by-month.component.ts` — concrete site of the eager SSR-time HTTP call that breaks under container-to-container networking.
- `client-flutter/Dockerfile`, `client-flutter/docker-compose.yml`, `client-flutter/lib/core/config/api_config.dart` — precedent for per-project Dockerfile + compose style; `hostOverride` mechanism is a precedent for "override the base URL for a non-default network context," directly analogous to the SSR problem in `web/`.
- Root `CLAUDE.md` — already stale in two ways found during this exploration (still says `front/` not `web/`; still claims `web/` has no environment-based API config). Any root-level Docker work should also correct these, though that's a documentation fix orthogonal to Docker itself.

## Approaches

1. **Three independent per-project Dockerfiles + one orchestrating root `docker-compose.yml`** (referencing each sub-project's own Dockerfile via `build.context`), no root Dockerfile of its own.
   - Pros: Matches the existing structure exactly — `back/` and `client-flutter/` already each own their Dockerfile/compose and are treated as independently-versioned projects per the root `CLAUDE.md`'s explicit statement ("no root package.json... always cd into the relevant sub-project"). Requires writing only ONE new Dockerfile (`web/Dockerfile`, likely bun-based, mirroring `back/`'s multi-stage `dev`/`prod` split) plus the root orchestrator file. Reuses `back/compose.yaml`'s mongodb/api definitions almost as-is via `include:` or duplicated service blocks referencing `context: ./back`.
   - Cons: Root compose still needs to solve the SSR-networking problem (service-name DNS + context-aware `apiUrl`) and the CORS port mismatch; some duplication between `back/compose.yaml` and the root file unless Compose's `include:` (Compose v2.20+) is used to avoid copy-pasting the mongodb/api service definitions.
   - Effort: Medium.

2. **Single root Dockerfile / unified multi-stage build for all three services.**
   - Pros: One file to maintain in theory.
   - Cons: Directly contradicts the repo's stated boundary ("two independent, separately-versioned projects... no unified build/test/lint") — back is Node/npm, web is Node/bun, client-flutter is Dart/Flutter with a completely different base image; a single Dockerfile would need awkward multi-language build stages with no shared dependency graph, no shared test runner, and no shared versioning. Actively fights the existing convention rather than extending it.
   - Effort: High, and produces a worse-fit artifact than Approach 1.

3. **No root compose at all — document three independent `docker compose up` invocations, one per sub-project.**
   - Pros: Zero new orchestration code; already partly works today (`back/` and `client-flutter/` each have working standalone compose files).
   - Cons: Does not address the actual ask ("dockerize the monorepo" implies some level of unified orchestration); still leaves the cross-service networking question (web ↔ back, client-flutter ↔ back) completely unresolved since nothing would put these containers on a shared Docker network; user would have to manually reconcile ports across three separate `docker compose` sessions.
   - Effort: Low, but likely does not satisfy the actual goal.

## Recommendation

Approach 1 (three independent per-project Dockerfiles/build-contexts + one orchestrating root `docker-compose.yml`) is the only approach consistent with the repo's explicit, stated structure. It requires building exactly one new artifact (`web/Dockerfile`) since `back/` and `client-flutter/` already have theirs, and it should reuse `back/compose.yaml`'s `mongodb`/`api` service definitions (via `include:` if available, else careful duplication) rather than reinventing them. The two real blocking design questions that a `sdd-propose`/`sdd-design` phase must resolve before writing any compose file are: (a) how `web/`'s SSR process resolves the API host differently from the browser (e.g., `isPlatformServer` swapping `apiUrl` to `http://api:3000` server-side while keeping `http://localhost:3000` for the browser bundle — mirroring the `hostOverride` pattern `client-flutter` already uses for its own host-resolution problem), and (b) whether root-level orchestration replaces or coexists with `back/`'s existing "native app + dockerized Mongo only" dev workflow (`onboarding.mjs`), since that workflow is documented as the mandatory `./start-dev.sh` path today and changing it has ripple effects on `back/ONBOARD.md` and `back/CLAUDE.md`.

## Risks
- **[Confirmed, not hypothetical] SSR-time server-to-server call breaks in a multi-container network**: `SummaryByMonthComponent` fires an HTTP call to `apiUrl` (`http://localhost:3000`) as an eager field initializer, which Angular Universal executes server-side during SSR too. Inside a `web` container, `localhost:3000` resolves to the `web` container itself, not `back` — this will fail with connection-refused unless the base URL is made context-aware (browser vs. server) before/while dockerizing `web/`.
- **CORS port mismatch already exists independent of Docker**: `back/scripts/onboarding.mjs` generates `.env` with `CORS_ORIGINS=http://localhost:5173`, but `web/`'s actual dev port is 4200. This will silently block real CORS requests from the current frontend regardless of Docker; any root compose that wires these together needs to fix this value, not just replicate it.
- **Two coexisting back/ dev workflows**: `onboarding.mjs`'s documented path only containerizes Mongo and runs the API natively; the `api` service in `compose.yaml` exists but is not exercised by the mandatory `./start-dev.sh` script. A root-level "fully containerize everything" compose either needs to also become the new documented path (updating `back/start-dev.sh`/`ONBOARD.md`) or needs to explicitly coexist with the native path without the two drifting apart (e.g., MONGO_CONN_STR override logic).
- **Root `CLAUDE.md` is stale in ways a Docker task would surface anyway**: still refers to `front/` (real dir is `web/`), and still claims no environment-based API config exists in the frontend (it does, via `environment.ts`, the *value* is just hardcoded). Not a Docker blocker, but any change touching root docs should fix this in passing or flag it separately.
- **`client-flutter`'s Android/iOS targets are entirely out of Docker's reach** (native mobile builds don't execute inside a container at runtime) — only its `web-server` target is a legitimate Docker orchestration participant. Scope of "dockerize the monorepo" should explicitly exclude native mobile builds.

## Ready for Proposal
Yes — enough concrete ground truth (existing Dockerfiles, compose files, actual networking/env code) has been gathered to move to `sdd-propose`. The proposal phase should explicitly decide: (1) context-aware API base URL strategy for `web/` SSR vs. browser, (2) whether the root compose supersedes or coexists with `back/`'s native+Mongo-only dev workflow, and (3) whether to fix the `CORS_ORIGINS`/port-5173 mismatch as part of this change or file it separately.
